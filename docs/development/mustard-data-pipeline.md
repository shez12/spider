# Mustard 多源轨迹空间增强：完整数据处理流程

更新时间：2026-11-03（北京时间）。本文说明当前实际流程；历次检查、计时及故障记录见 [持续开发记录](mustard-data-processing-log.md)，空间增强对照见 [自适应采样试验](spatial-adaptive-pilot.md)。

暂停前最后汇总为478/2200条有效，其中第一源复用旧任务100条，本轮新增378条；第1、10、15、18源各100条完成。其他有产出的源为第2源65条、第6、11、12、20源各1条、第17源9条；其余12源仍为0条。

## 2. 流程总览

```text
已发布 retarget_full 数据集及 manifest
    → 筛选同物体右手示范、按原始任务去重
    → 从已发布轨迹提取手掌/指尖/物体参考
    → 构建 KUKA + 原生 Sharpa 右手 + 实体桌子
    → 为每个源生成共享平面刚体变换候选
    → 物体桌面范围预筛选
    → CPU IK：初始帧必要条件检查 + 全轨迹几何审核
    → IK 合格候选进入共享 GPU 队列
    → MuJoCo Warp / SPIDER：512采样、最多200轮
    → 审核选中的实际轨迹 + 独立 GPU 重放
    → 双严格通过后保存有效轨迹、重放、视频并计数
    → 未满100的源继续补候选；每源分别计数
```

IK合格只表示几何筛选通过，cost低只表示优化目标较低，两者均不等于真实物理成功。

## 3. 数据来源与源示范筛选

使用用户选择的**已发布 retarget_full 轨迹**，不是重新下载和解析原始DexYCB人手MANO标注。

- 数据入口：`example_datasets/retarget_full`，实际数据位于 `/data4t/spider-datasets/retarget_full`。
- 从 `manifest.json` 读取记录，要求 `dataset=dexycb_lifted`、`embodiment_type=right`，任务名含 `_right_006_mustard_bottle_`。
- 必须存在源场景和 `trajectory_mjwp.npz`。
- 按完整原始任务名去重；同任务优先选Allegro，其次Sharpa、XHand、Inspire。
- 当前可用不同源为22条，完整映射保存在 `selected_sources.json`。
- 准备源时，若manifest提供源场景/轨迹SHA256，则核对哈希；保留原始记录和哈希溯源。

主要实现：`examples/arm_hand/mustard_multisource.py` 的 `select()`、`prepare_source()`，以及 `batch_kuka_gpu.py` 的 `prepare()`。

## 4. 提取参考轨迹

从源机器人场景与已发布状态轨迹计算正向运动学，提取四类参考数组：

- `wrist_pos`：手掌/腕部位置。
- `wrist_quat`：手掌姿态。
- `fingertips`：拇指、食指、中指、无名指四个指尖位置。
- `object_qpos`：物体位置和姿态。

这些参考来自已发布机器人轨迹，并不等同于原始人手标注。四元数数组采用MuJoCo的wxyz顺序，与SciPy互转时显式调整顺序。

原参考保存为 `source_reference.npz`。IK结果另存为 `reference.npz`，包含后续使用的关节参考；求解前后检查四类目标参考未被IK原地改变。原始时间轴不延长、不增加extra hold、不做左右镜像。

主要实现：`prepare_kuka_right.py`、`batch_kuka_gpu.py`。

## 5. 机器人、桌面与控制环境

机器人使用KUKA机械臂和原生Sharpa右手模型。机械臂默认关节姿态及PD控制参数沿用Play2Perfect配置，具体数值以场景与代码常量为准。

- 桌面高度作为z=0，机械臂底座位置为 `(0, 0.8, -0.53)` 米，底座与桌面保持53厘米高度差。
- 加入真实桌子盒体；记录中的桌子中心为 `(0, 0, -0.15)` 米、半尺寸为 `(0.2375, 0.2, 0.15)` 米。
- 机器人本体（机械臂及手）设置 `gravcomp=1`；物体保持 `gravcomp=0`，物体仍受重力与接触动力学影响。
- 保留源参考高度、时间与初始速度语义，不通过增加额外保持阶段改变任务。
- 场景保存为每个源及每个候选的 `scene.xml`，审核以该候选实际场景为准。

重力补偿用于改善此前起始向下砸落的问题；它不代表物体被固定，也不能替代碰撞审核。

## 6. 空间增强候选生成

当前生产使用均匀采样：yaw在±10度内，x、y偏移分别在±5厘米内。每个源独立生成候选，随机参数由源的种子和candidate编号确定，保存在 `augmentation.json`，便于复现。

同一候选对手掌位置、手掌姿态、所有指尖和物体位姿应用**同一个平面刚体变换**：

```text
p'(t) = Rz(yaw) · (p(t) - c) + c + s
q'(t) = qz(yaw) ⊗ q(t)
```

其中c取机械臂底座对应的平面旋转中心；s由源物体初始XY锚点与采样偏移计算，使增强后的初始物体XY等于“原初始XY + 采样偏移”。因此元数据中的共享平移s不一定等于采样的XY偏移。

同一个变换保持每帧手—物体的相对交互几何；所有z值与时间索引保持不变。代码对相对位置旋转关系和z不变性作数值断言。

当前没有把自适应试验中的最小间距保护全面迁入生产，不能把生产100条自动解释为具有试验同样的覆盖保证。检查多样性时应另看yaw、XY跨度、归一化最近距离和空间分箱覆盖；不能用同一成功点附近大量近重复候选代替广覆盖。

主要实现：`spatial_augmentation.py::augment()`、`mustard_valid100.py::generate()`。

## 7. CPU IK与几何筛选

先用物体碰撞几何的包围盒检查整条物体参考是否明显超出桌面XY范围，要求桌边1毫米余量；确定越界者可直接拒绝。该步骤是保守预筛选，剩余项仍需完整审核。

IK以Play2Perfect默认机械臂姿态初始化，初始帧保留8次初始化尝试，轨迹求解步长为2。初始帧求解后检查必要条件；确定失败者提前结束，不继续求完整轨迹。

主要几何条件包括：

- 初始手掌位置误差小于1厘米，四指初始位置误差分别小于3厘米。
- 全轨迹平均手掌位置误差不超过8厘米。
- 机器人与桌面穿透满足原1毫米限制，手部自碰撞最大穿透小于1毫米。
- 关节参考在控制范围内。
- 物体完整碰撞几何在各帧均满足桌面XY边界及1毫米余量。

审核输出 `retargeting.json`、`geometry_report.json` 和 `ik.log`。确定不合格记录为 `ik_rejected`；SVD不收敛等执行异常记录为 `ik_failed`，不当作物理拒绝。

IK主要在CPU执行。已将残差计算改为位置/接触所需的 `mj_fwdPosition` + `mj_sensorPos`，避免每次完整动力学计算；代表测试的传感器、接触距离及短轨迹参考数组与原实现一致。

## 8. GPU优化

通过几何筛选后，将候选送入MuJoCo Warp GPU动力学优化。机械臂与手共同优化，保留原始SPIDER采样更新与代价定义，不以新损失替换原目标。

当前生产参数：

- 每轮512个采样，优化seed为0。
- 最多200轮；不是此前某些单轨迹实验的300轮。
- 控制扰动使用10个时间结点；噪声按 `0.97**iteration` 衰减。
- 收敛等待30轮，相对容差0.001、绝对容差0.01。
- 不启用“cost小于100就停”。
- 生产命令使用 `--active all --table-collision-weight 0`；优化中未额外加该桌碰惩罚，不代表最终允许桌面碰撞。
- 已配置严格提前检查的生产任务，每10轮仅在选中轨迹与独立GPU重放均通过全部原标准时提前完成。

保存 `gpu/checkpoint.pt`、`history.json`、`result.json`、实际选中轨迹 `trajectory.npz` 和独立重放 `replay_trajectory.npz`。检查点恢复使用原候选及参考，不能重新随机采样后沿用旧检查点。

**控制器溯源例外：**另一世界模型工作流为第18源配置过反馈控制pilot。该源100条有效中27条无reference_policy、73条使用世界模型reference_policy，均通过原双严格标准。原始采样更新和代价不变，不等于所有候选使用相同控制生成方式。比较方法或吞吐时必须区分源与控制器，不能把全部生产结果当成纯原始控制基线；本流程总结没有修改该配置。

## 9. 双重物理验证与计数

第一侧审核优化中实际选中的轨迹，第二侧审核重新初始化后的独立GPU重放。两侧都必须满足：

- 物体位置RMSE < 0.03米。
- 最终物体位置误差 < 0.03米。
- 最终物体旋转误差 < 20度。
- 机械臂—桌面、手—桌面、手部自碰撞的最大穿透分别 < 0.001米。

这些是严格不等式。cost再低，只要任一侧任一指标不满足，也不能计为有效。

GPU负责产生物理轨迹；审核阶段在CPU上用源MuJoCo模型进行正向运动学和接触几何检查，不用CPU动力学重新仿真来代替GPU结果。碰撞检查基于保存的10毫秒状态帧，不代表连续时间、帧间无碰撞保证。

两侧报告分别保存为 `gpu/tracking_collision_report.json` 与 `replay_audit/tracking_collision_report.json`。`replay_audit/trajectory.npz` 是指向 `gpu/replay_trajectory.npz` 的审核链接。

成功后渲染 `best_gpu.mp4`，再写 `accepted` 状态并进入有效清单。验证不合格为 `physics_rejected`；优化、审核或渲染执行异常为 `physics_failed`，需区分基础设施故障与任务物理失败。

**视频使用实际GPU状态，但视频看起来成功不能替代数值双审核。**

## 10. 并行调度、计时与恢复

多源总调度器为 `mustard_multisource.py`，每源协调器为 `mustard_valid100.py`。IK采用CPU进程池，物理候选通过独立GPU子进程运行，使用私有CUDA MPS共享GPU。

- 资源政策为总计10槽、预留2槽，生产共用其余8个GPU槽，不是每源8槽。
- IK使用独立全局槽控制；小批合格项即可送GPU，不等整批100个候选完成IK。
- 状态按文件mtime缓存；资源槽等待者扫描可用槽，减少等待已占槽而忽略其他空槽的情况。
- 总调度恢复时接管存活子进程，避免重复启动；恢复前核对进程身份、目录及检查点。
- `throughput.json` 与约5分钟一次的 `throughput_history.json` 记录最近约两小时有效产出/墙钟小时。
- IK累计计算时间、物理累计计算时间、排队时间和端到端墙钟必须区分；并行服务时间相加不等于用户等待时间。
- 暂停、故障、恢复和共享GPU负载应保留在端到端口径中，不能只用成功样本耗时估计整体工期。

曾发生MPS fatal及Error807，强制结束客户端可能影响其他共享客户端，因此禁止为了加载新代码反复kill GPU任务。初始化807有最多6次干净进程退避重试；已知7条SIGSEGV保留隔离，不盲目重试。基础设施错误不能算物理失败率分母。

当前暂停采用冻结进程保留内存的方式，并已停止排空监视器。后续恢复前需核实PID身份和CUDA上下文仍存活；若电脑重启，原PID/内存不可恢复，应从磁盘检查点接管，而不是直接向旧PID发信号。本文不自动恢复任务。

## 11. 文件组织与读取顺序

主目录：`outputs/mustard_multisource_valid100/`。

```text
selected_sources.json                 源示范及组目录映射
summary.json                          总数、各源数及最后汇总阶段
accepted.json                         已审核有效项总清单
throughput.json                       最近窗口吞吐及累计计算时间
throughput_history.json               历史快照
user_stop.json                        用户暂停状态及进程记录
sources/<源编号_任务>/                 源准备场景、参考、哈希及日志
groups/<源编号_任务>/
  parallelism.json                    共享资源与并行参数
  acceleration.json                  严格检查/记录/可选控制器配置
  accepted.json                      本源有效清单
  candidate_<编号>/
    augmentation.json                变换、随机种子、源哈希
    scene.xml                        实际候选场景
    source_reference.npz             增强后的目标参考
    reference.npz                    IK与优化参考
    state.json                       候选状态、指标、错误与耗时
    geometry_report.json             几何筛选结果
    retargeting.json                  IK初始对齐等报告
    gpu/checkpoint.pt                优化检查点
    gpu/history.json                 每轮cost、invalid数与耗时
    gpu/result.json                  参数与优化结果
    gpu/trajectory.npz               选中实际轨迹
    gpu/replay_trajectory.npz         独立GPU重放
    gpu/tracking_collision_report.json
    replay_audit/tracking_collision_report.json
    best_gpu.mp4                     有效候选实际轨迹视频
```

第一源复用的100条在 `outputs/mustard_spatial_valid100`，不一定出现在多源groups目录中；应按 `selected_sources.json` / `summary.json` 的实际路径读取。未通过或尚未完成的候选不保证拥有上述所有产物。

查有效数据先读accepted清单，再核对候选state、双报告和产物；查当前运行状态先读user_stop及真实进程，再参考summary。`parallel_physics` / `running`只是调度标签，不证明该源已通过IK或物理验证。

## 12. 已做实验与当前瓶颈

### 自适应空间增强：已测试，未迁移生产

4个源、每源uniform/adaptive各16个新候选，共128个。自适应25%全域探索、75%局部采样，冻结历史反馈；两侧采用相同间距保护。IK标签只引导几何区域，物理成功标签才代表成功。

均匀得到8/64有效，自适应12/64有效；但进入物理优化的数量为23对40，记录服务时间约7.45对11.45小时，有效/服务小时约1.07对1.05。服务时间可能漏中断未提交耗时，也不能当作端到端墙钟。因此未证明总体加速，不能据候选预算提升50%直接宣称速度提升50%。源18自适应yaw覆盖也更集中。试验已完成，未自动替换生产均匀采样。

### MuJoCo / Isaac Sim：单轨迹对照已完成

相同候选、512采样、固定200轮，MuJoCo约11.3分钟，当前Isaac适配约42.6分钟，两者均未通过全部严格标准。该单例、共享负载测试不支持迁移整个任务以求提速，也不代表所有Isaac场景更慢。

### 已部署实现提速与尚未解决的问题

已部署位置/碰撞所需IK计算、初始必要条件失败早拒绝、小批IK到GPU调度、状态缓存、可用槽扫描和双严格成功提前结束。部分失败IK候选耗时有明显降低，但不能当作整体有效吞吐同比提升。

当前主要困难是源间可行性与物理通过率差异：部分源累计大量初始几何拒绝；进入物理优化者又常因最终旋转、自碰撞或跟踪失败。源6、12在长期失败后出现首条有效，说明有限随机失败不能证明数学不可达；也不能承诺所有源最终一定能在当前范围补足100条。

后续若恢复研究，应先按源定位参考/初始对齐、接触与物理失败，使用隔离对照比较有效/墙钟小时及空间覆盖。保留原参考、优化目标和全部标准，不用降低阈值、减少覆盖或把容易源数量搬给困难源来提高总计数。
